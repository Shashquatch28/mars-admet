# KERMT inference service

Serves the 30 Tier-0 KERMT checkpoints (6 arms x 5 seeds) on CPU. The API image stays torch-free: it asks
this service for per-seed values and does the ensembling, AD flag and error band itself, exactly as it does
for XGBoost. Which endpoints go to KERMT is `ml/serve/routing.json` (generated by
`ml/eval/kermt_routing_evidence.py`; evidence in `documentation/status/kermt_routing_evidence.md`).
With `KERMT_SERVICE_URL` unset, nothing here is used and every endpoint is served by XGBoost.

```
API  --POST /predict {smiles:[one], arms:[...]}-->  kermt service (this directory)
                                                    engine.py loads <arm>/seed_<n>/model.pt once
API  <-- per-seed values per target --------------  runs KERMT's own task.predict forward loop
API: mean +/- std over seeds, AD flag, KERMT error band -> EndpointPrediction (model_id = mars-kermt-*)
```

Failure behaviour: if the service is down, slow (`KERMT_TIMEOUT_SECONDS`), still loading or returns something
malformed, the endpoints routed to KERMT are answered by XGBoost for that request (their `model_id` says so), a
circuit breaker skips the service for 10 s, and the response is **not** cached (`prediction_service.is_degraded`).
It never falls back to the stub and never fabricates a value.

## Files

| file | role |
|---|---|
| `Dockerfile` | CPU image: torch 2.9.1, **rdkit 2025.09.1 (load-bearing)**, KERMT at the commit every run recorded |
| `engine.py` | loads checkpoints once; SMILES -> `rdkit_2d_normalized` features -> KERMT `predict` -> inverse target scaler |
| `app.py` | FastAPI: `POST /predict`, `POST /explain` (synchronous, kept for tools), `POST/GET/DELETE /explain/jobs[/{id}]` and `GET /explain/config` (background Integrated Gradients, ADR-035), `GET /health`, `GET /models` |
| `jobs.py` | The in-memory job manager behind `/explain/jobs`: one worker thread, a bounded queue (`KERMT_EXPLAIN_QUEUE`, default 8), a deterministic job id so a repeat submit joins the running job, cancel between chunks, finished jobs kept for an hour. No torch; tested in `ml/tests/test_kermt_jobs.py`. A restart loses jobs, and the API reports that as a lost job |
| `explain_ig.py` | Integrated Gradients for one endpoint of one arm (ADR-031): leaf graph tensors, descriptor gradients read from the readout FFN inputs, cubic-substitution midpoint rule, completeness measured. `POST /explain {smiles, arm, endpoint}`; the engine lock is taken per chunk of interpolation points, so predictions interleave. Tested on a random-weight model only (`ml/tests/test_kermt_explain_ig.py`); not yet run on the real checkpoints |
| `fetch_artifacts.py` | downloads the 30 models from W&B into `ml/artifacts_kermt/`, SHA-256 checked against each artifact's metadata |
| `parity_check.py` | holds the engine to the stock-CLI GPU predictions recorded in a W&B run-record artifact |

## Run it

```bash
# 1. models (ml/.venv, logged in to W&B as shashquatch): ~5.8 GB into ml/artifacts_kermt/ (gitignored)
cd ml && PYTHONPATH=. .venv/Scripts/python serve/kermt_service/fetch_artifacts.py

# 2. service (opt-in compose profile; builds the image on first use)
docker compose --profile kermt up -d kermt

# 3. point the API at it (.env): KERMT_SERVICE_URL=http://kermt:8100
```

Environment (service): `KERMT_ARMS`, `KERMT_SEEDS` (default 0,1,2 in compose), `KERMT_THREADS` (default: the
container's cgroup CPU limit, not the host's), `KERMT_BATCH_SIZE`, `KERMT_TOKEN`.

## Sizing (measured 2026-10-19, 4 vCPU container, 70M-parameter checkpoints)

- **Memory:** about 0.8 GB for torch plus 0.19 GB per loaded checkpoint. The five arms the routing table uses
  at 3 seeds = 15 checkpoints = 3.4 GB; at 5 seeds, 25 checkpoints = about 5.5 GB. DILI is not routed to KERMT,
  so it is not loaded by default.
- **Latency:** one new molecule across the five routed arms at 3 seeds (15 checkpoints) took 3.4-4.5 s inside the
  service and 4.4-4.9 s through the API in a 4-CPU container (one arm, 3 checkpoints: 0.9 s). Per checkpoint that is
  0.15-0.3 s depending on host load; a profile put about 60% of it in the model's matmuls, so it is compute, not
  Python overhead. Running checkpoints concurrently was no faster than one at a time on all four CPUs (measured
  2x2 and 4x1 threads), so the engine runs them sequentially. Batching molecules lowers the per-molecule cost
  by about 30%. A cached repeat is 0.06 s.
  Thread count must follow the container's CPU limit: `os.cpu_count()` reports the host's CPUs, so the engine
  reads the cgroup quota (`effective_cpus()`).
- **Load time:** about 10-12 s per checkpoint (readiness is `/health`, 503 until all are loaded).
- A request is answered one at a time; concurrent requests queue.

## Seeds per arm

Three of five seeds is the default: it keeps the seed-spread and the ensemble mean the blueprint's basic
ensembling asks for, at 60% of the memory and latency of five. `KERMT_SEEDS=0,1,2,3,4` loads all five. The
seed choice is not a quality statement; the seeds are exchangeable and the spread is not an interval (ADR-024).

## Parity (run after any change to the image, KERMT commit, rdkit or this engine)

```bash
# record = downloaded W&B run-record artifact kermt-<arm>-seed0-record:v0; models laid out as <arm>/seed_0/
docker run --rm -v <models>:/models -v <record>:/record mars-kermt-infer \
  python parity_check.py --root /models --arm metabolism__cls --seed 0 --record /record --split test --n 128
```

2026-10-19, rdkit 2025.09.1: worst absolute difference to the GPU reference **3.6e-7**, PASS. With rdkit 2025.9.6
(what an unpinned build resolves to) the same checkpoint drifted by up to **4e-3**, because the normalized
descriptors move between rdkit patch releases. That is why the Dockerfile pins it.
